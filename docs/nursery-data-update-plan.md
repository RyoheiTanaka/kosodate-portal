# 保育園データ更新・機能拡張 実装計画

作成日: 2026-08-13

## 背景

現行DBの保育園データは、つくば市が公開していた **2023年4月版オープンデータ（29列）** をベースにしている。
その後つくば市はオープンデータのフォーマットを変更し、**令和8年4月版（R8-4opendata.xlsx）は10列に削減**された。
定員・開所時間・送迎バスなどは、別ソース（入所のご案内PDF）から取得する必要がある。

現行DBは108件、最新データは119件。実質的に約3年分の差がある。

### 調査で判明した事実

| 項目 | 内容 |
| --- | --- |
| `nursery_id` の正体 | つくば市が付与している **園番号**。独自採番ではない。欠番 6/10/11/12 も市側の欠番 |
| 緯度経度 | オープンデータに含まれる。ジオコーディング不要 |
| `district` | オープンデータに無い。住所の大字から判定する必要がある |
| 常時空の5項目 | `access` / `approval_date` / `fax` / `corporate_number` / `url` は2023年版でも全件空。市が元々提供していない |
| `name_kana` | DBは全件空だったが、令和8年版で全件提供される。カナ検索が初めて機能するようになる |

### 突合方法

xlsx と PDF は **電話番号** で突合する。119件すべて一意に紐付くことを確認済み。
名称はPDF側に見出しや注意事項が混入するため、突合キーには使わない。

## 差分サマリ（2023年4月版 → 令和8年4月版）

108件 − 廃止4 + 新設15 = 119件

- **新設15件**: 園番号 912〜926（市が採番済み。自分で決める必要はない）
- **廃止4件**: 上横場保育所(4) / 小田保育所(18) / 高見原保育所(21) / 城山保育所(22) — すべて公立
- **改称・種別変更6件**（IDは引き継ぐ）

| 園番号 | 旧 → 新 |
| --- | --- |
| 100 | スクルドエンジェル保育園つくば駅前園 → KUKURUインターナショナルプレスクールつくば駅前園 |
| 909 | みどりのみつぼし保育園 → みどりのみつぼし**こども園**（種別変更） |
| 69 | しいの木 → しいの木保育園 |
| 70 | YMCAオリーブ保育園 → YMCAつくばオリーブ保育園 |
| 77 | ぐっとふれんど保育園 → ぐっどふれんど保育園（旧データの表記誤り） |
| 81 | ソシエルみどりの → 小規模保育園 ソシエルみどりの |

- 既存園の変更: 定員15件 / 電話8件 / 住所7件（移転2件）/ 座標3件 / カナ95件（新規付与）

## 決定事項

- 廃止園は **`is_active: false` のソフト削除**。詳細ページは残し、閉園である旨を表示する（既存URLを404にしない）
- 更新の入力は **CSV**。管理画面は作らない（更新頻度が年1回程度のため見合わない）
- 電話番号は **xlsx を正とする**。入所のご案内PDFの開園予定園の番号は法人連絡先のため採用しない
- 地区は **市の6区分を維持**。URLに `district_alphabet` が含まれるため再編しない
- 地区の判定は **大字マップ方式**。座標のポリゴン判定は不要
- 機械的に解消できない差分は **目視確認**する

## 全体の進め方

```
ステップ1: データ更新の土台   ← 現在ここ
ステップ2: エリア軸の追加
ステップ3: 距離順ソート
```

エリア軸も距離順ソートも新データが前提になるため、ステップ1を先に完了させる。

## ステップ1: データ更新の土台

### 1-1. スキーマ変更

`server/models/Nursery.ts` / `server/types/nursery.ts`

**追加**

| フィールド | 型 | 用途 |
| --- | --- | --- |
| `is_active` | Boolean（default true） | 閉園・廃止のソフト削除 |
| `source_date` | String（例 `2026-04-01`） | データ基準日 |
| `address` | String | フル住所。将来的に分割カラムを置き換える（[#84](https://github.com/RyoheiTanaka/kosodate-portal/issues/84)） |
| `address_note` | String | 方書（ビル名・街区）。119件中14件のみ |
| `timestamps: true` | — | `createdAt` / `updatedAt` |

**削除**（取得元が存在せず、全108件で空）

`access` / `approval_date` / `fax` / `corporate_number` / `url`

**`required` の緩和**

新設園は定員などが後追いになるため、手入力系フィールドの `required: true` を外す。

### 1-2. 取り込みスクリプト

`scripts/import-nurseries.mjs`

- 入力: `scripts/data/nurseries-2026.csv`
- キー: `nursery_id`（＝市の園番号）で upsert
- CSVに存在しない既存園は `is_active: false` に更新（削除はしない）
- CSVに無い項目（設立年月日・団体名・利用可能曜日・備考・一時預かり）は既存値を保持
- `--dry-run` で書き込まずに差分だけ表示
- 依存追加なし（mongoose は既存の依存を使う）

**住所の扱い（段階移行）**

CSVは住所1列＋方書1列。DBは `prefecture` / `city` / `address1` / `address2` / `address3` に分割している。

今回は **フル住所カラム `address` を追加し、分割カラムと共存させる**。

- `address`（フル住所）と `address_note`（方書）を追加
- **CSVの `address` を唯一の正**とし、分割カラムは取り込みスクリプト内で機械的に導出する
  （`prefecture='茨城県'`、`city='つくば市'`、`address1`=大字、`address2`=番地以降、`address3`=方書）
- 両方をCSVで持たないため、共存期間中も値がズレない

一本化は今回のデータ更新が完了してから別途対応する。
データ更新の検証と表示のリファクタを同時に行うと、差分の原因切り分けが難しくなるため。

> 対応Issue: [#84 住所カラムを address に一本化し、分割カラム（prefecture/city/address1-3）を廃止する](https://github.com/RyoheiTanaka/kosodate-portal/issues/84)

**環境変数**

`MONGODB_URI`（DB名を含まない接続文字列）と `MONGODB_DB`（接続先のDB名）を、
環境変数 → `.env` の順で読む（`scripts/lib/db.mjs`）。

DB名を接続文字列から切り離しているのは、dev/prod の切り替えを秘密情報を含まない
1変数の変更で済ませるため。`mongodump` / `mongorestore` も DB名を含まない URI を
要求するため、同じ `MONGODB_URI` をそのまま渡せる。

実行時に接続先DB名を表示し、開発用DB（`_dev` で終わる名前）以外に**書き込む**場合は
`--prod` を要求する。読むだけの操作（`--dry-run`、バックアップ作成）は対象外。

この開発環境では Atlas の SRV レコードがローカルDNSで解決できないため、
スクリプト内で `dns.setServers(['8.8.8.8'])` を指定する。

> 対応Issue: [#89 開発用DBを分離し、DB名を kosodate に変更する](https://github.com/RyoheiTanaka/kosodate-portal/issues/89)

### 1-5. 反映手順

ローカルの `.env` は開発用DB（`kosodate_dev`）を指しているため、**そのまま実行すると開発用DBが対象**。
本番（`kosodate`）に反映するときだけ、DB名と本番用の接続文字列を実行時に渡して `--prod` を付ける。

```bash
MONGODB_URI="mongodb+srv://<本番ユーザー>:<password>@<cluster>/?retryWrites=true&w=majority" \
MONGODB_DB=kosodate \
  npm run import:nurseries -- --prod
```

1. **バックアップを取得**

   ```bash
   mongodump --uri="$MONGODB_URI" --collection=nurseries --out=backups/dump
   ```

   `mongodump` が無い環境では、追加インストール不要の簡易版を使う。

   ```bash
   npm run backup:nurseries
   ```

2. **差分を確認**

   ```bash
   npm run import:nurseries -- --dry-run
   ```

3. **反映**

   ```bash
   npm run import:nurseries
   ```

4. **確認** — 一覧 / 地区別 / 詳細 / キーワード検索 / 地図マーカー / 閉園園のURL

### 復元方法

```bash
mongorestore --uri="$MONGODB_URI" --drop --nsInclude="nurseries.nurseries" backups/dump
```

```bash
npm run backup:nurseries -- --restore=backups/nurseries-20260813-085818.json
```

> 復元先も `--prod` の対象。開発用DB以外に `--restore` すると、フラグ無しでは中断する。

> MongoDB Database Tools は MSI でインストールしても PATH に追加されない。
> 実体は `C:\Program Files\MongoDB\Tools\100\bin`。
>
> Atlas の M0（無料枠）にはクラウド側の自動バックアップが無いため、反映前のダンプ取得は必須。

### 1-6. 目視確認が必要な18行

CSVの `check` 列に印がある行。

- **定員変更 15件** — 抽出は正しく、実際に定員が変わっているもの（例: 岩崎保育所 60→90、かなめ保育園 170→120）
- **すてっぷ保育園 3園（74/82/83）** — 8時間枠がPDFに「8:00〜16:00または8:30〜16:30」と併記。DBへの格納方法を決める必要がある

## ステップ2: エリア軸の追加

### 課題

現行の6地区は分布が偏っている。

| 地区 | 件数 |
| --- | --- |
| 谷田部 | 57 |
| 桜 | 26 |
| 大穂 | 7 |
| 豊里 | 7 |
| 茎崎 | 6 |
| 筑波 | 5 |

谷田部だけで約半分を占め、絞り込みとして機能していない。TX開通後の人口増が旧町村区分に収まっていないため。

### 方針

地区は市の公式区分としてデータ属性のまま残し、**UIの主導線となるエリア軸を別に追加**する。
地区を再編しないのは、URL（`/nurseries/[district]/[id]`）を壊さないため、および市の資料と照合可能な状態を保つため。

- `area` フィールドを追加（つくば駅周辺 / 研究学園 / みどりの / 万博記念公園 / 北部 / 南部 など）
- ルートは `/nurseries/area/[area]` を新設し、既存の `/nurseries/[district]` は温存
- 区分の定義は大字マップと同様にJSONで持つ

エリアの具体的な区切りは実装時に決める。

## ステップ3: 距離順ソート

現在地または入力した住所からの距離で並べ替える。
座標がオープンデータで全件提供されているため実装コストが低く、
「近い順に見たい」という要求は区分をどう切っても代替できないため、優先度は高い。

- 現在地の取得（Geolocation API）
- 住所入力からの座標変換が必要かは要検討（Google Maps API を既に利用しているため流用可能）
- 一覧・地区別・エリア別のいずれでもソート可能にする

## 将来の拡張について

保育園以外の子育て情報（一時預かり、児童館、公園、子育て支援センター、病児保育など）を追加していく構想がある。

**方針: 施設種別ごとにコレクションを分ける。** `Nursery` に他種別を詰め込まない。

保育園固有の項目（保育標準時間・送迎バス・認可区分など）は他の施設種別には存在せず、
単一コレクションにまとめると空フィールドだらけになる。今回まさに、市が提供をやめた5項目が
全件空のまま残っていた問題と同じ構図になる。

種別が増えた段階で、共通部分（名称・住所・座標・地区・エリア・連絡先）の扱いを検討する。
共通コンポーネントやユーティリティの切り出しで足りる可能性が高く、
スキーマの共通化を先回りして作り込む必要はない。

今回のステップ1〜3では既存構造を維持する。

## 補足: 年次更新の運用

初回（今回）は重いが、次年度以降は以下で回せる。

1. つくば市のオープンデータと入所のご案内PDFを取得
2. 抽出スクリプトでCSVを生成
3. `check` 列（20行前後）だけ目視確認
4. `npm run import:nurseries -- --dry-run` で差分確認
5. 本番反映

つくば市に**推奨データセット形式（29列）での提供再開を要望**する価値はある。
再開されれば取り込みは1ファイルで完結し、PDF抽出が不要になる。
